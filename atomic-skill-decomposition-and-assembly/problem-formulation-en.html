Atomic Skill Decomposition and Assembly: From Reasoning Chains to Reusable Atomic Skills

Last updated: 2026-07-22

Chinese | Atomic skills v1 | Companion: continuous memory | Brainstorming hub

Research track

The goal is complex video reasoning: both intricate plot reasoning that requires understanding social cues, intention, and contradiction, and long-term video reasoning that requires accumulating evidence across extended segments. The initial idea is not to propose a new memory store, nor to have an 8B model solve long videos end-to-end; instead, decompose teacher reasoning chains into reusable atomic skills, then have a compact controller reassemble them on new problems into executable, verifiable, locally repairable video-reasoning skill chains / graphs. Memory is one high-value execution scenario for organizing long-horizon evidence; verifiers and repair are the supporting mechanisms that make decomposition-and-assembly trainable and evaluable.

What we are actually doing

Show full description

Current VLMs usually run video/image + question → free-text CoT → answer. That pipeline has five recurring problems:

  1. Intermediate steps are not executable — they are prose, not operations.
  2. Visual / memory evidence is not inspectable — claims do not point back to frames, clips, or memory nodes.
  3. Errors cannot be localized — a wrong answer gives no failing step.
  4. Temporal / causal constraints are easily talked over by fluent language.
  5. Self-correction rewrites the whole answer instead of fixing the broken step.

We do not copy the teacher’s full reasoning chain; we decompose it into reusable atomic skills and assemble a new executable skill chain / graph for new problems:

  • Shift: free-text reasoning chain → reusable atomic skills → new executable skill chain / graph.
  • Real target: not “the model uses tools” or “a new memory store,” but “the model learns to decompose, reuse, assemble, execute, verify, and repair reasoning skills.”

Atomic skill = typed symbolic operator

Show full description

An atomic skill is not a natural-language prompt step; it is a typed symbolic operator with explicit inputs, outputs, preconditions, effects, executor, verifier, and failure codes. The controller learns how to compose them, not invent them online. So a memory operation is not free-form writing — it is typed, constrained, executable, and verifiable.

Skill schema

skill = {
  name,
  input_types,
  output_types,
  preconditions,
  effects,
  executor,     # 运行该技能的 neural / tool 调用
  verifier,     # 检查结果是否 grounded 且合法
  failure_codes # 该技能可能失败的 typed 原因
}

Operator example

DetectContact(entity_a, entity_b, time_span)
  Inputs:        Entity × Entity × TimeSpan
  Outputs:       ContactEvent
  Preconditions: visible(entity_a, time_span)
                 visible(entity_b, time_span)
  Effects:       contact_event(entity_a, entity_b, time_span)
  Verifier:      视觉接近 + 时间重叠
                 + 运动 / 状态变化
  • Small stable basis: a few typed operators beat many fuzzy tools; never hand-write one skill per task.
  • Evidence-first: every input / output / evidence points back to memory or the raw clip.
  • Structured returns: time span, entity id, modality, confidence, clip pointer, graph node id, short rationale.

Where neural-symbolic shows up

Show full description

This framing is neural-guided symbolic program assembly, not free imagination. The split is explicit:

  1. Symbolic part: typed memory skills, preconditions / effects, skill-graph structure, type constraints, temporal / causal constraints, symbolic executor, hard verifier.
  2. Neural part: observer (perceive object / event / time span), reasoner (select skill), argument binder (bind object / timestamp / evidence / memory node), graph assembler (generate program), soft verifier (judge grounding / contact / causality), repair policy (repair failed program).
  • Hard checks (symbolic): type, preconditions, temporal order, whether evidence pointers exist.
  • Soft checks (neural): whether clip / memory node actually supports the claim.

Three atomic-skill types + two cross-cutting mechanisms

Show full description

Keep the initial idea but make the implementation crisper: skills are predefined, not invented online. The core task is to fit teacher reasoning chains to this fixed atomic skill library, then reassemble chains / graphs for new problems. To avoid the skill taxonomy becoming a long list of memory operations, the first paper converges the library to three main skill types; verification and repair are not separate domain skills but cross-cutting mechanisms on every type.

  1. 1 — Perception-tool skills: call detectors, trackers, OCR, ASR, VLM captioners, segmenters, etc., to turn raw video / audio / image into typed observations. Examples: TrackEntity, DetectContact, TranscribeSpeech, LocalizeEvent, ExtractVisualEvidence.
  2. 2 — Evidence-backed memory skills: store / query memory with evidence pointers. Examples: StoreMemory(event, evidence), RetrieveEvent, RetrieveEvidence, ResolveCoreference, QueryTemporalChain. The key is not “what was stored,” but that every store / query must bind inspectable evidence.
  3. 3 — Multi-hop reasoning skills: compositional reasoning over existing observations, evidence spans, and memory nodes. Examples: InferTemporalRelation, InferCausalRelation, ComparePastAndCurrentState, ComposeEvidenceChain, AnswerFromEvidence.

Recommended execution flow

raw video/audio
  -> perception-tool skills
  -> evidence-backed memory store/query
  -> multi-hop reasoning skills
  -> grounded answer / local repair
  • Verification is cross-cutting: each skill type carries its own hard / soft verifier, not a fourth domain-skill category.
  • Repair is the controller’s meta-skill: on failure, replace arguments, insert missing hops, swap skills, re-query evidence, or rewire edges — not regenerate the whole answer.
  • First-paper minimal basis: perception-tool keeps only reliable tool calls; memory skills focus on evidence-backed store/query; reasoning skills focus on temporal / causal / state / evidence-chain composition.

Single compact policy: skill assembly, not direct reasoning

Show full description

Discussion conclusion: do not train two separate agents, and do not describe 8B as the final semantic reasoner. Decomposition, assembly, and repair are phases of one compact controller. Memory write / update / merge / forget / query are atomic skills in the first-paper scenario; more generally, the controller learns to select skills from the atomic skill library, bind arguments, assemble new chains, and repair locally on failure.

Keep the write/read boundary, not two models. The original split idea came from (a) contamination and (b) different clocks. (a) is handled by interface discipline: only evidence-backed observations may commit; hypothetical reasoning must not write. (b) only truly forces separation under streaming.

  • Policy level: unified — reasoning / tool / memory operations all map to skills in one typed action space.
  • Execution level: offline = one loop; streaming = one policy with two runtime contexts.
  • 8B does: select skills, bind arguments, decide retrieval / verification / reasoning steps, and repair failed chains / graphs.
  • 8B does not: raw video perception, open-ended causal / social reasoning, or independently adjudicate final answers.
  • Supervision machinery: ground-truth answers, teacher demonstrations / corrections, executors, retrieved evidence, and verifiers.
  • Upside: cheaper, reusable control policy; expensive teacher produces traces, helps decomposition, correction, and evaluation — not full planning at inference forever.

Method pipeline

Show full description
  1. Step 1 — Collect teacher traces. Input is not just the answer but question + context / memory state → reasoning chain / tool trace → evidence chain → answer. Traces can come from teacher models, tool-call trajectories, human examples, or benchmark evidence annotations.
  2. Step 2 — Fit trace to predefined atomic skills. Given predefined skill library S = {s_1..s_K}, fit long chains into typed operators: s_i = ⟨input types, output types, preconditions, effects, executor, verifier, failure_codes⟩. The goal is not to invent skills or copy every sentence, but to interpret the teacher trace as a composition of fixed skills.
  3. Step 3 — Build a small stable skill library. Merge synonymous skills, drop overly narrow task-specific skills, keep cross-problem skills such as retrieval, grounding, temporal reasoning, evidence verification, and answer composition.
  4. Step 4 — Assemble a new task-specific skill chain / graph. Given new query q, context, and memory substrate M_t, the 8B controller selects skills, binds arguments, and generates P_q = [s_1(args_1)..s_T(args_T)] or G_q = (V_skills, E_dependencies).
  5. Step 5 — Execute, verify, repair. Each node executes and returns structured observations; hard verifiers check type / timestamp / evidence pointer / contradiction; on failure, repair only local nodes or edges, not rewrite the whole answer.
  6. Step 6 — Grounded answer. Final answers come from the executed evidence chain / memory subgraph, aligned with benchmark ground truth and evidence annotations in training and evaluation.

Training recipe (5 stages)

Show full description
  1. Stage 1 — Teacher-supervised trace-to-skill fitting SFT. Teacher / tool traces become chain → predefined typed skill sequence / graph as SFT data. 8B first learns to map natural-language reasoning steps to fixed skill ids, arguments, and evidence pointers.
  2. Stage 2 — Skill-library calibration. Manually lock the minimal basis of three skill types, filter one-off skills; during training do not expand the skill ontology — only learn skill selection, argument binding, evidence binding, and dependency edge prediction.
  3. Stage 3 — Teacher-supervised assembly SFT. Given new questions and memory state, have 8B generate executable skill chains / graphs, not free-text CoT. Teacher produces candidate programs; hard verifier + evidence / answer anchors filter to executable, grounded SFT targets only.
  4. Stage 4 — On-policy verified video-reasoning RL. The student samples complete structured actions on its own rollout states: a_t = (skill_type, tool_name, tool_arguments). After executing tools or reasoning skills, reward comes from schema validity, execution success, verifier-supported evidence / reasoning progress, and tool cost; GRPO updates policies for perception, retrieval, evidence organization, social / temporal reasoning, verification, repair, or stop.
  5. Stage 5 — Teacher-supervised local repair. Input bad skill chain + failure feedback → output repaired chain: replace argument, insert missing skill, delete redundant node, rewire edge, change evidence span. Teacher may propose repair candidates, but candidates must pass verifier / anchor to enter the training set.

After executing the tool or reasoning skill, tool execution + verifier provide reward; teacher / OPD are optional warm-up only, not the core training signal.

Skill-chain case bank: turn verified reasoning chains into retrievable references

Show full description

Core idea: on a new video, retrieve not only raw evidence but also verified skill-chain / repair patterns from past videos as plan priors for current complex video reasoning. This is not a new memory-storage claim but a natural extension of atomic skill decomposition: store reasoning programs that succeeded or were repaired after failure as cases for how to decompose, search, organize evidence, and repair local failures on new tasks.

Boundary to lock: the skill-chain case bank may provide reasoning-pattern references only, not factual evidence for the current video. Current answers must still be supported by the current video’s evidence bank, tool execution, and verifiers; retrieved old chains only answer “what evidence roles, skill order, and repair operators similar problems usually need.”

Where training signals come from

Show full description

To claim a learning contribution, train a compact agent — a memory-skill program controller. It is not the final reasoner; it learns to generate and repair skill graphs. Signals ranked by how true and defensible they are:

  1. Tool + environment feedback (free, stepwise, backbone): each typed skill returns structured success/failure (empty retrieval, type mismatch, duplicate conflict, missing evidence). Dense process supervision, zero human labels.
  2. Evidence-chain recall on existing multi-hop benchmarks (most discriminative): reward correct evidence chains, not just answers. Catches prompt-only 72B that answers correctly on ungrounded paths.
  3. Outcome reward (answer correctness): benchmark ground truth; sparse but reliable endpoint signal. Tells whether the final answer is correct, not whether each graph step is correct.
  4. Teacher demonstrations and corrections: large models provide candidate graphs, repairs, preference labels. Teacher output is supervision, not proof; filter with ground-truth answers and evidence checks.
  5. On-policy correction (cleanest learning story): 8B reaches its own error states; teacher / verifier correct programs there — not just offline distillation.
  6. Auto-generated counterfactual negatives: corrupt good traces (wrong order, wrong binding, broken evidence pointers, skipped hops) and train preferences.

Honest trap. If you train with only offline SFT on teacher traces, reviewers will correctly say “you just distilled 72B into 8B.” Escape requires ground-truth filtering, evidence-chain metrics, on-policy failure correction, repair success, cost/latency gains, and transfer.

  • Train: controller (program assembly + argument binding + verification choice + repair).
  • Do not train as contribution: memory writer — SFT on teacher deltas then freeze.
  • Experiment that makes training credible: frozen teacher-planner vs trained 8B program controller, same tools + memory, score by answer + process metrics.

Relation to LLM verified RL / process reward

Method spec: failure-data pipeline and verifier stack

Show full description

Principle to lock: teacher mainly generates SFT / supervised / repair warm-up data: traces, trace-to-skill fitting, assembly targets, and repair proposals. But teacher cannot also be final judge. Main reward comes only from tool execution + hard verifier + benchmark anchor; teacher / soft verifier are warm-up, repair hints, or diagnostics only. This avoids “teacher generates graph, teacher also judges graph correct.”

Failure-data pipeline

  1. Gold trace collection: collect teacher / tool traces that reach ground-truth answers and pass evidence checks; convert to typed skill chains / graphs as fitting / assembly SFT data.
  2. Synthetic corruption: automatically corrupt one local node or edge: wrong entity, wrong timestamp, missing evidence pointer, skipped hop, wrong temporal order, unsupported answer step. Advantage: controllable failure location and gold repair.
  3. Natural student failure: 8B controller on-policy rollout; after execution, hard verifier / benchmark anchor mark failed nodes, edges, or unsupported evidence. Advantage: realistic — proves the model repairs its own errors.
  4. Counterfactual distractor: build similar entities, nearby time spans, similar events, or similar evidence spans to induce retrieval / grounding / coreference confusion.
  5. Failure code assignment: each failure sample must carry one primary failure code, e.g. WRONG_ENTITY, BAD_TIMESTAMP, MISSING_EVIDENCE, SKIPPED_HOP, CONTRADICTION, INVALID_PRECONDITION.
  6. Repair target generation: teacher / human provide repair candidate / patch supervision only; candidate must re-execute and pass hard verifier + benchmark anchor to become a positive repair target.
  7. Audit: human spot-check natural failures, teacher-generated repairs, soft-verifier disagreements; prioritize high-reward, low-evidence-support, or verifier-disagreement samples.

Structured reflection / repair over fitted skill chains

Show full description

Key boundary: reflection is not free text “where I went wrong.” We use verifier-grounded structured reflection: execute the fitted skill chain, collect each node’s verifier output, and limit reflection to failure localization, failure code assignment, root-cause tracing, and repair operator selection.

Relation to recent verifiable RL / self-correction work. RLVR / GRPO / Visual-RFT show that when reward is verifiable, rollout + group-relative / RL post-training improves reasoning or vision. SCoRe / multi-turn self-correction show correction is best trained on the model’s own on-policy correction traces, not offline SFT alone. But we cannot copy natural-language self-correction: skill library, executor, evidence pointers, and hard verifiers are structured, so repair should be local patches, not full-chain rewrites.

Algorithm：Trace-to-skill fitting

Input: teacher trace T, predefined skill library S, evidence annotations E
Output: fitted skill graph G

1. Normalize T into candidate action spans.
2. For each span, select skill_id from S.
3. Bind arguments, evidence pointers, and output variables.
4. Add dependency edges between skill outputs and later inputs.
5. Execute/check each skill when possible.
6. Keep G only if hard checks + answer/evidence anchors pass.

Algorithm：Structured reflection and local repair

Input: fitted graph G, execution trace R, verifier outputs V
Output: repaired graph G'

1. Locate failed node/edge using hard verifier + benchmark anchor.
2. Assign failure_code.
3. Trace upstream dependencies to identify root cause.
4. Select repair_operator from fixed set.
5. Generate local graph patch, not a full-chain rewrite.
6. Re-execute affected subgraph.
7. Accept patch only if hard checks and evidence/answer anchors improve.

Design lessons from the legacy Video_Skills implementation

Show full description

Background: the legacy Video_Skills repo implemented a Phase-1 deterministic substrate (14 curated atomic skills, 7 canonical typed objects, three-layer memory, 6 verifier checks, deterministic harness, rule-based controller, online serving loop; 58 tests green). Later experiments often failed or underperformed, but the following design insights still hold in practice and should be absorbed into the current plan.

  1. Lock wire format; ban ad hoc dicts. The old repo defined 7 canonical typed objects (GroundedWindow, EvidenceBundle, HopGoal, AtomicStepResult, VerificationResult, AbstainDecision, ReasoningTrace) as the only legal interchange format between modules. The current story says “typed, constrained, executable, verifiable” but never defines what is passed. Takeaway: paper one must lock a set of canonical objects, especially minimal EvidenceRef fields (modality, time_span, entities, provenance, confidence) and AtomicStepResult failure_mode enum. The old repo over-weighted typed objects (many fields unused in practice); lesson: keep only fields checked at runtime.
  2. "Stable memory, evolving reasoning" layering validated in practice. If memory and skills co-evolve, training signal degrades. The old repo recorded: "if the bank were allowed to grow freely while the controller was being trained, the controller's action space would shift mid-training and the GRPO reward signal would degrade." The current story should cite this to justify first-paper scope: teacher-built memory + freeze.
  3. Skills must declare verification rules and failure modes at definition time. Each old-repo SkillRecord required verification_rule and failure_modes at creation, not invented post hoc. Practice: without co-defined verification rules, later verifiers find many skill outputs lack structure to check.
  4. next_action escalation beats free-text repair in practice. Old verifiers returned next_action ∈ {continue, retry, broaden, switch_skill, abstain}, aggregated by severity. Free-text “where the model went wrong” is unreliable. Recommendation: keep only 5–6 of the 10 repair operators in paper one (old 5 + INSERT_SKILL); add rest after on-policy failure data.
  5. 14 v1 atomics exposed skill-granularity issues. The old repo had 14 atomic skills; practice showed: (a) identify_question_target and decompose_into_subgoals should not be skills — they are controller internals; (b) check_evidence_sufficiency and decide_answer_or_abstain should not be skills but cross-cutting verification / decision. The current story’s “verification and repair are cross-cutting, not a fourth skill type” is confirmed. Truly reusable reasoning skills are only 6–7 — an empirical lower bound for the “minimal stable basis.”
  6. Evidence-first hard constraint: claims without evidence must abstain. Old repo Contract Rule #3: “Every claim either has a non-empty EvidenceBundle or a verifier action of abstain.” Enforced per step via validate_atomic_step(). Write this as a hard constraint: claim-type skill outputs must bind evidence refs or abstain; bare claims rejected by hard verifier.
  7. Three-layer memory in practice: episodic most reliable; semantic and state hard to fill. Episodic memory (events + time + participants + evidence refs) comes directly from perception — most grounded. Semantic (abstractions) and state (belief + spatial) depend on high-quality 72B/32B output; if perception is wrong, these layers are dirty. Recommendation: limit paper-one memory mainly to episodic + evidence layer.
  8. Harness as deterministic interpreter is the right architecture. Controller only selects skills + binds args; execution and side effects are harness-controlled — replayable skill execution, complete traces, auditable memory writes. “Execute and verify” in the method pipeline is the harness role but not explicitly named.

Failure lessons from the old implementation (confirming current direction by contrast):

  • Rule-based controller insufficient — confirms need to train an 8B controller.
  • Lexical retrieval insufficient — paper one should use embedding-based retrieval from the start.
  • Hand-authored skills without trace fitting too rigid — cannot adapt to new problem types; confirms trace-to-skill fitting value.
  • No repair meant verifier fail → only abstain — old repo switch_skill and broaden often insufficient; confirms local repair necessity.

One line: the old repo’s value is not the code but a runnable implementation answering the story’s fuzziest design questions (wire format, inference flow, skill granularity, memory layering, verification hard constraints), while its failures confirm the current direction (trained controller, trace fitting, local repair).

Trace-to-skill fitting with demonstration-induced basis

Updated position: the core method is Trace-to-Skill Fitting, not open-ended online skill invention. We should not hand-claim that a fixed 12-skill list is universally correct, and we should not ask a 35B model to freely invent or patch atomic skills. Instead, demonstrations induce candidate operation clusters; a compact typed atomic basis is selected before controller training; repeated verified subgraphs can later become composite motifs that always expand back into the frozen atomic basis.

Optional: verified reasoning motifs as assembly priors

Show full description

Decision: the first paper does not need composed skills as a core mechanism. What video reasoning needs most is atomic skill graph assembly + evidence-grounded verification + local repair. Reusable composed patterns are useful, but only as optional assembly / repair priors, not as new primitives, not as online actions, and not as evidence sources.

The main failure modes in video reasoning are usually not “missing a macro-skill name.” They are wrong evidence spans, entity / speaker binding errors, temporal-order mistakes, unsupported claims, missing bridge evidence, and social / causal inferences not grounded in the current video. These are better addressed by atomic nodes, typed dependencies, evidence pointers, verifier checks, and local repair.

Correct role of a motif

Question: "Why was the alibi inconsistent?"
  -> retrieve a verified motif:
       claim -> contradiction evidence -> linking action -> verify
  -> instantiate an atomic skill graph on the current video
  -> execute, verify, and repair the expanded atomic nodes

Motif example

ResolveAlibiContradiction(person, claim)
  expands to:
    extract_dialogue_claim
    retrieve_temporal_neighborhood
    localize_clue
    mark_evidence_role
    compose_evidence_chain
    infer_social_contradiction
    verify_evidence_supports_claim
  • Not a primitive: a motif is not a new atomic skill and should not enlarge the controller's online action space.
  • Not evidence: a motif carries no facts from old videos; current answers still require current-video evidence.
  • Always expandable: before execution, every motif must expand into frozen atomic skill nodes and typed edges.
  • Repair happens below the motif: failed execution repairs the expanded node / edge / argument, not the macro label.
  • Best use cases: reducing planning cost, improving transfer, and providing repair priors such as MISSING_LINKING_ACTION -> query earlier segment for person-object interaction.

Recommended wording: We do not rely on open-ended skill creation. Instead, we assemble task-specific executable graphs over a compact atomic skill basis. Reusable reasoning motifs mined from successful traces are used only as assembly priors and are always expanded into atomic skill graphs before execution and verification.
