Research track

We do not propose a new memory store, and we do not claim an 8B model independently solves long-horizon video reasoning. We train a compact controller to assemble and repair executable memory-skill graphs that organize teacher demonstrations, tool execution, verification, retrieval, and ground-truth answer feedback over long-term multimodal memory.

Core thesis (one line)

Show full description

MemorySkillGraph: Neural-Symbolic Skill Assembly for Long-Horizon Multimodal Memory Reasoning (mechanism: failure-aware training of a compact memory-program generator).

We formulate long-horizon multimodal memory reasoning as neural-symbolic skill assembly over an external memory substrate. Instead of training an 8B model to answer long-video questions directly, we train it to generate and locally repair typed memory-skill programs. Teacher demonstrations, executors, verifiers, retrieved evidence, and benchmark ground-truth answers provide supervision and evaluation; the compact model learns the control policy that organizes these components.

  • Memory is the substrate. Neural-symbolic skills are the operating system over memory.
  • From: memory as a passive retrieval database.
  • To: memory as an executable neural-symbolic workspace where agents query, store, verify, and reason via typed atomic skills.
  • Role of 8B: not final reasoner; it is a program generator / controller / repair policy.
  • One-line takeaway: don't teach the small model to answer directly; teach it to assemble an executable, verifiable, repairable memory program that guides retrieval, verification, and answer generation.

What we are actually doing

Show full description

Current VLMs answer through video/image + question → free-form CoT → answer. That pipeline has five recurring failures:

  1. Intermediate steps are not executable — they are prose, not operations.
  2. Visual / memory evidence is not inspectable — claims do not point back to frames, clips, or memory nodes.
  3. Errors cannot be localized — a wrong answer gives no failing step.
  4. Temporal / causal constraints are easily talked over by fluent language.
  5. Self-correction rewrites the whole answer instead of fixing the broken step.

We replace the free-form reasoning chain with an executable neural-symbolic memory-skill graph:

  • Shift: free-form reasoning chain → executable neural-symbolic memory-skill graph.
  • Real target: not "the model uses tools," but "the model learns to compose, execute, verify, and repair programs over memory."

Atomic skill = typed symbolic operator

Show full description

An atomic skill is not a natural-language prompt step. It is a typed symbolic operator with explicit inputs, outputs, preconditions, effects, an executor, a verifier, and failure codes. The controller learns to compose these operators, not to invent them online. Memory operation is therefore not free-form writing; it is typed, constrained, executable, and verifiable.

Skill schema

skill = {
  name,
  input_types,
  output_types,
  preconditions,
  effects,
  executor,     # neural / tool call that runs the skill
  verifier,     # checks the result is grounded and valid
  failure_codes # typed reasons the skill can fail
}

Example operator

DetectContact(entity_a, entity_b, time_span)
  Inputs:        Entity × Entity × TimeSpan
  Outputs:       ContactEvent
  Preconditions: visible(entity_a, time_span)
                 visible(entity_b, time_span)
  Effects:       contact_event(entity_a, entity_b, time_span)
  Verifier:      visual proximity + temporal overlap
                 + motion / state change
  • Small, stable basis: fewer typed operators beat many vague tools; never hand-write one skill per task.
  • Evidence first: every input / output / evidence binds back to memory or raw clips.
  • Structured returns: timestamp range, entity ids, modality, confidence, clip pointer, graph node ids, compact rationale.

The skill graph (why it beats linear CoT)

Show full description

A skill graph has atomic skills as nodes and dependencies as edges. Edges are not just sequence; they carry typed dependency relations.

Example: "Why did the cup fall?"

LocalizeEvent(cup_falling)
   ↓
TrackEntity(cup)
   ↓
TrackEntity(hand)
   ↓
DetectContact(hand, cup)
   ↓
CompareState(cup, before, after)
   ↓
InferCausalRelation(contact, falling)
   ↓
VerifyEvidence(answer, frames)
  • Edge types: data, temporal, causal, evidence, memory dependency.
  • Why stronger than linear CoT / tool chains: multi-hop structure is explicit, branchable, inspectable, and gives verifiers clean boundaries to score.
  • typed edges
  • multi-hop
  • temporal / causal
  • inspectable

Where neural-symbolic lives

Show full description

This framing is neural-guided symbolic program assembly, not free-form imagination. The split is explicit:

  1. Symbolic part: typed memory skills, preconditions / effects, skill-graph structure, type constraints, temporal / causal constraints, symbolic executor, hard verifier.
  2. Neural part: observer (perceive objects / events / time spans), reasoner (select skill), argument binder (bind object / timestamp / evidence / memory node), graph assembler (produce the program), soft verifier (judge grounding / contact / causality), repair policy (fix failed programs).
  • Hard checks (symbolic): types, preconditions, temporal order, evidence pointers exist.
  • Soft checks (neural): does the clip / memory node actually support the claim.

The five families of memory skills

Show full description

Keep the basis small and memory-operating (not generic video skills). Five families:

  1. A — Perception-to-memory (write observation into memory): ExtractEntity, ExtractEvent, ExtractState, ExtractEvidence, StoreMemory. → raw video/audio → structured memory records.
  2. B — Memory query (find in memory): RetrieveEntity, RetrieveEvent, RetrieveState, RetrieveEvidence, QueryTemporalChain, QueryRelationalNeighborhood. → query → relevant memory subgraph / clips / evidence.
  3. C — Update / consolidation (merge, compress): ResolveCoreference, MergeDuplicateMemory, UpdateState, ConsolidateEpisodes, CompressSubgraph. → reduce duplication, keep long-term consistency, form higher-level semantic memory.
  4. D — Verification (is the memory trustworthy): VerifyEvidence, VerifyTemporalOrder, VerifyStateTransition, CheckContradiction, CheckMemoryGrounding. → prevent hallucinated / stale memory and wrong entity linking.
  5. E — Memory reasoning (reason over memory): InferTemporalRelation, InferCausalRelation, ComparePastAndCurrentState, FindPrecedingCause, ExplainEventFromMemory, AnswerFromEvidence. → memory subgraph → answer / explanation / action decision.
  • Key: these are memory-operating skills, not ordinary video skills.
  • Perception / relation operators (e.g. TrackEntity, DetectContact) live inside families A and E as executors.

One compact policy: program assembly, not direct reasoning

Show full description

Decision from discussion: do not build two separately-trained agents, and do not frame 8B as the final semantic reasoner. Decomposition, assembly, and repair are phases of one compact controller. Memory write / update / merge / forget / query are atomic skills inside the same typed action space. The learned contribution is a single policy that generates and repairs typed memory-skill programs over the memory substrate.

Keep the write/read boundary, not two models. Separation was motivated by (a) pollution and (b) different clocks. (a) is solved by interface discipline: only evidence-backed observations may be committed; reasoning-time hypotheses cannot. (b) only forces real separation in streaming.

  • Policy level: unify — memory ops are skills in one typed action space.
  • Execution level: offline = one loop; streaming = two runtime contexts of one policy.
  • 8B does: choose skills, bind arguments, decide retrieval / verification steps, and repair failed graphs.
  • 8B does not do: raw video perception, open-ended causal / social reasoning, or final answer adjudication by itself.
  • Supervision machinery: ground-truth answers, teacher demonstrations / corrections, executors, retrieved evidence, and verifiers.
  • Upside: cheaper reusable control policy; the expensive teacher is used to demonstrate, correct, and evaluate rather than plan every inference step forever.

Method main line

Show full description
  1. Step 1 — Maintain an external memory substrate (graph, or vector+graph hybrid): M_t = (V_t, E_t, X_t) where V_t = entity / event / state / evidence nodes, E_t = temporal / relational / support edges, X_t = raw evidence pointers, embeddings, metadata.
  2. Step 2 — Define neural-symbolic memory skills S_mem = {s_1..s_K}, each s_i = ⟨input types, output types, preconditions, effects, executor, verifier⟩.
  3. Step 3 — Assemble task-specific memory programs. Given query q, the 8B controller does not answer directly; it emits a program P_q = [s_1(args_1)..s_T(args_T)] or a graph G_q = (V_skills, E_dependencies).
  4. Step 4 — Execute and verify. Each step reads / writes memory and is checked: M_t, state_i = Execute(s_i, M_t, state_{i-1}); Verify(s_i, M_t, evidence).
  5. Step 5 — Answer grounded in memory evidence: the final answer comes from retrieved memory subgraph + raw evidence pointers and is checked against benchmark ground truth during training / evaluation.

Training recipe (5 stages)

Show full description
  1. Stage 1 — SFT over teacher memory-operation traces. Teacher produces question + memory state → skill graph → evidence chain → answer. Keep traces that reach the ground-truth answer and pass basic evidence / format checks. The 8B learns DSL format, decomposition, argument binding, and evidence citation — not free-form video reasoning.
  2. Stage 2 — Subproblem curriculum. Decompose into verifiable subproblems (retrieval, coreference, state comparison, temporal / causal relation, evidence verification). Train short programs first.
  3. Stage 3 — 8B rollout of multiple memory programs. P_1..P_K ~ π_θ(P | q, M_t); different programs retrieve different events, bind different entities, cite different evidence, or choose different verification paths.
  4. Stage 4 — Score with ground truth + process feedback. Use answer correctness as the endpoint anchor, evidence-chain recall when available, hard validity checks, and teacher / verifier feedback as noisy process signals. The objective is valid executable program > invalid / unsupported program, not just correct > wrong answer.
  5. Stage 5 — Local repair / learn from failures. Input bad program + failure feedback → output repaired program: replace argument, insert missing node, delete redundant node, rewire edge, change evidence span.

Memory-operation reward and repair

Show full description

Memory program reward sketch

R(P) =  retrieval_correctness
      + evidence_support
      + temporal_consistency
      + state_consistency
      + memory_update_validity
      - contradiction
      + answer_correctness

Important interpretation. answer_correctness is the benchmark ground-truth endpoint; it filters and anchors the rollout. The other terms are process signals used to explain why a program worked or failed. They do not require the 8B to decide the final answer by itself.

Preference pairs (P_good > P_bad)

P_bad:  retrieves wrong person due to entity confusion
P_good: ResolveCoreference -> RetrieveEvent -> VerifyEvidence -> Answer

P_bad:  stores an ungrounded event without evidence pointer
P_good: ExtractEvent -> VerifyEvidence -> StoreMemory

Local repair example

Failure:
  RetrieveEvent returned an event AFTER the target event,
  violating the temporal constraint.
Repair:
  add QueryTemporalChain + filter events before target timestamp.
  • Novelty: learning from failed memory operations, not just wrong answers.
  • Precise learning target: bad program + feedback → repaired program, not video → answer.

Training signal: where it comes from

Show full description

To claim a learning contribution we train one compact agent — the memory-skill program controller. It is not the final reasoner; it learns to generate and repair skill graphs. Signals, ranked by how real and defensible they are:

  1. Tool + environment feedback (free, per-step, the backbone): every typed skill returns structured success/failure (empty retrieval, type mismatch, duplicate conflict, missing evidence). Dense process supervision, zero human labels.
  2. Evidence-chain recall on existing multi-hop benchmarks (most discriminative): reward the correct evidence chain, not just the answer. A prompt-only 72B can get the answer right via an ungrounded path; this catches it.
  3. Outcome reward (answer correctness): benchmark ground truth; sparse but reliable endpoint signal. It says whether the final answer is right, not whether every graph step is right.
  4. Teacher demonstrations and corrections: large models provide candidate graphs, repairs, and preference labels. Teacher output is supervision, not proof; it should be filtered by ground-truth answer and evidence checks.
  5. On-policy correction (cleanest learning story): the 8B visits its own error states and the teacher / verifier corrects the program on those exact states — this is what makes it more than offline distillation.
  6. Auto-generated counterfactual negatives: corrupt good traces (wrong order, bad binding, broken evidence pointer, skipped hop) and train preference.

The honesty trap. If trained only by offline SFT on teacher traces, a reviewer correctly says "you just distilled 72B into 8B." Escape it with ground-truth filtering, evidence-chain metrics, on-policy failure correction, repair success, cost/latency gains, and transfer.

  • Train: the controller (program assembly + argument binding + verification choice + repair).
  • Do not train as the contribution: the memory writer — SFT from teacher deltas and freeze.
  • Justifying experiment: frozen teacher-planner vs trained 8B program controller, identical tools + memory, scored on answer + process metrics.

Relation to LLM verified RL / process reward

Show full description

Mainstream LLM verified RL is question → reasoning chain → answer → verifier → reward, historically with sparse outcome reward. Verifiable Process Reward work argues that when intermediate actions can be checked by a symbolic / algorithmic oracle, the oracle becomes dense turn-level supervision and fixes long-horizon credit assignment — depending on verifier quality.

Our insight: free-form CoT steps are unstable and hard to verify; memory-skill steps are typed operators, naturally suited to process-level verified reward.

  • Free-form CoT: step is hard to define / verify.
  • MemorySkillGraph: node / edge / argument / evidence are all verifiable → node-, edge-, subgraph-motif-, and answer-level reward.
Related work
  • RLVR / Tülu 3 — RL from verifiable rewards; backbone for verifier-driven post-training.
  • Process Reward Models — Step-level reward; motivates scoring per node/edge.
  • GRPO (DeepSeekMath) — Group-relative optimization over rollouts; lifted to program-level rollouts.
  • DPO — Preference optimization; basis for "valid > invalid" program training.

Insights from recent VLM reasoning / post-training

Show full description
  1. Visual-RFT / VLM-R1: multiple rollouts + verifiable reward + GRPO beats SFT-only; task-specific rule-based rewards (e.g. IoU). → sample multiple memory programs, execute / verify, GRPO over the program policy, design skill-specific verifiers.
  2. Point-RFT / grounded CoT: text-only CoT causes hallucination; grounded CoT lifts ChartQA 70.88% → 90.04%. → not every sentence is grounded, but every skill node's input / output / evidence is.
  3. Critic-V: Reasoner + Critic; DPO-trained critics catch VLM errors. → our critic operates at node / edge / evidence level.
  4. Self-correction / learn-from-failure: must be trained, not just prompted. → "wrong answer → correct answer" becomes "failed memory program → repaired program."
  5. PRM / VPR: dense verifier-grounded rewards improve long-horizon credit assignment. → memory skills supply natural step boundaries.
Related work
  • Visual-RFT — Verifiable-reward RFT for LVLMs; template for program-level rollout.
  • VLM-R1 — R1-style RL for VLMs; verifiable-reward post-training infrastructure.
  • Critic-V — Reasoner + Critic for multimodal reasoning; node/edge/evidence-level critique.

Difference from M3-Agent + related-work map

Show full description

M3-Agent = build a multimodal long-term memory graph + retrieve + iterative thinking/control. Ours = given / maintain a memory substrate + define neural-symbolic memory skills + assemble executable memory programs + verify query/store/reasoning steps + train from failed memory operations.

M3-Agent asks how to build and retrieve multimodal memory; we ask how an agent should operate over memory through typed, executable, verifiable skills. M3-Agent's focus is the memory system; ours is the memory operation policy.

Evaluation & strongest experiment setup

Show full description

Report process metrics, not just fluency. Do not cover all memory operations at once — first version focuses on three task families:

  1. Task 1 — Long-video memory QA: can the agent find past events, cite correct evidence, answer cross-time questions?
  2. Task 2 — Memory update consistency: after new observations, is memory updated correctly, are duplicate entities merged, are contradictory states avoided?
  3. Task 3 — Failure repair: given wrong retrieval / wrong write / wrong temporal chain, can it repair via verifier feedback?

Baselines: RAG over captions, GraphRAG, M3-Agent-like retrieval, CoT over retrieved memory, flat memory tools, linear memory-skill chain, ours (memory-skill graph), ours + verifier / post-training.

Metrics: answer accuracy, evidence-chain recall / precision, retrieval correctness, hop / node success, trace correctness, memory-update validity, contradiction rate, abstention calibration, repair success, tool-call cost.

The justifying experiment: frozen teacher-planner vs trained 8B program controller under identical tools + memory; the compact policy is justified only if it reaches similar answer/evidence quality with lower cost, better repair, better transfer, or better process metrics.

Notes: needs a benchmark that can score memory-operation correctness, not only final answers — see the next card for candidate datasets and the gap they leave open.

ICLR readiness: framing is enabling condition, not headline

Show full description

Honest scope of this fix. Reframing does not raise the underlying research quality — it adds zero data. It is necessary but not sufficient: its only job is to stop a good result from being misjudged as "another neural-symbolic / another memory graph" in the reviewer's first five minutes. Expected effect ≈ +0.5–1, concentrated on not being killed in the borderline band, not on turning a 6 into an 8. If the two P0 tables fail, framing cannot save the paper; the real quality is decided by experiments.

Neural-symbolic = foundation, not signboard. "Neural-symbolic skill assembly" is an old banner (NS-CL, neural module networks, ViperGPT, VisProg, LLM+P, program-of-thought); leading with it re-invites the novelty-attribution attack and the "how symbolic is it really?" critique (executor + soft verifier are VLMs). Keep it as the enabling condition: because memory ops are typed symbolic operators with checkable preconditions / evidence pointers, every step is verifiable — and that is precisely what makes failure-aware verified process RL + program repair possible, which free-form CoT cannot support.

Headline wording (sell the RL + repair, use NS as the "because")

Because memory operations can be cast as typed symbolic operators
with checkable preconditions and evidence pointers, every reasoning
step becomes verifiable. We exploit this to train a compact controller
with failure-aware verified process reward and program repair —
something free-form CoT cannot support.

Four design decisions to lock BEFORE running experiments (these are framing / design problems experiments cannot fix):

  1. One-line novelty = failure-aware verified process RL + repair over typed memory ops; demote "skill graph" to carrier.
  2. Three-layer verifier, reward only on hard + anchor: hard (types, timestamps, preconditions, evidence-pointer existence, contradictions) + benchmark anchor (answer correctness, evidence-chain recall) carry the reward; soft / teacher verifiers are noisy preference only, never in the hard reward. Structurally kills the circularity / reward-hacking critique.
  3. Decouple eval from supervision: the teacher that generates traces must not be the grader; evidence-chain uses benchmark-native labels; self-built typed-trace eval scores only hard constraints.
  4. Cut scope to query + verify + repair over a teacher-built memory; defer store / update / merge / forget / streaming to paper 2.

Substantive reframe to raise true quality (and the experiments it demands)

Show full description

Two kinds of reframe — only one raises true quality.

  1. Cosmetic reframe (re-wording): new headline, demote neural-symbolic, prettier positioning. Changes perception only → does not raise true quality (see card 023).
  2. Substantive reframe (re-defining the research question / unit of contribution): changes what you measure and claim, therefore changes which experiments you run → this is the only lever besides running experiments that raises true quality. No free lunch: it redirects effort, it does not replace it — but it aims the same work at a higher-ceiling target.

Four substantive reframes (by leverage):

  1. From "a system" to "a phenomenon" (biggest lever). Not "MemorySkillGraph does memory reasoning" but "when and why does learning from failed memory programs beat distillation / SFT?" Turns an engineering paper into a science paper whose product is a finding, not a leaderboard rank.
  2. From "win the benchmark" to "prove a property." Target transfer / compositional generalization / reliability that only the typed-verifiable-repair structure enables. Property-centric framing forces experiments that yield a principle — the path from recipe to principle.
  3. From "repair is a stage" to "repair is the central object." Make bad program + feedback → repaired program the headline mechanism the whole paper studies in depth, instead of diluting across five skill families. This is the least-objectable novelty; concentrate it.
  4. From "self-built eval is a burden" to "the eval protocol is a first-class contribution." "First protocol that scores memory-operation correctness + repair." Its quality is independent of whether the method wins → a quality floor that does not depend on experiment luck.

Recommended combo: main reframe = #1 + #3 (a phenomenon study centered on the repair mechanism); #2 as the key experiment (transfer proof); #4 as the quality floor (released eval protocol).

Do we need more experiments? Yes — as redirection, not volume. Keep the P0 pair (card 023) as the go/no-go gate; add the principle-level experiments below; drop anything that is just "another win table." Net ≈ +4, with discipline (each transfer / streaming setup is costly).

Open questions

Show full description
  1. What is the minimum stable memory-skill basis (across the 5 families)?
  2. How are typed failure labels and program-repair targets generated automatically and cheaply?
  3. How do we keep verifiers reliable enough to avoid reward hacking?
  4. Can a thin typed-trace + memory-operation eval layer over EgoLife / LongVidSearch / Video-Holmes / MA-EgoQA score retrieval / update / repair correctness, not just final answers?
  5. When should a repeated verified subgraph motif become a composite memory skill?
  6. How much can an 8B program controller learn from teacher demonstrations + ground-truth answer anchors + failure repair before needing teacher planning at inference time?
  7. Which transfer best demonstrates the claim: short → long video, or offline → streaming memory?
  8. Teacher compression risk: how do we prove the 8B is not merely compressing teacher plans? Required ablations: teacher-only inference, 8B SFT-only, 8B + failure repair, 8B + on-policy correction, graph vs linear chain, no-verifier, and no-graph variants.
  9. Failure-data pipeline: how exactly do we create bad program + feedback → repaired program data? Options include corrupting teacher traces, collecting natural 8B rollout failures, executing programs, assigning failure codes, asking teacher / human for repair targets, and human spot-checking.
  10. Verifier stack: can we explicitly separate hard verifiers (types, timestamps, preconditions, evidence-pointer existence, contradictions), benchmark anchors (answer correctness, evidence-chain recall), and teacher / soft verifiers (noisy preference and repair signals, not oracle)?
  11. Trace non-uniqueness: how do we avoid treating a teacher trace as the only correct graph when many programs can reach the same answer? Should reward be over equivalence classes defined by answer, evidence chain, constraints, cost, and unsupported-claim avoidance rather than exact trace match?
  12. Graph vs linear tool chain: what measurable hypothesis proves graph structure is useful rather than JSON-CoT? Candidate claims: branching, shared evidence, typed dependencies, local node/edge repair, sub-result caching, and reusable subgraph motifs.
  13. Cost model: when is 8B actually cheaper after counting controller calls, executor calls, verifier calls, retrieved-clip tokens, and teacher fallback calls? What fallback rate keeps the method economical?
  14. Executor boundary: which skills are reliable enough for paper 1, what failure rate do they have, and which errors can repair actually fix? Be explicit that perception failures (tracking, contact, speech/person linking, temporal boundaries) are not the main contribution.
  15. First-paper scope: should paper 1 be narrowed further to query + verify + repair over an existing teacher-built memory, leaving store / update / merge / forget to a second paper?

Notes: the most urgent method questions are the failure-data generation pipeline and the non-circular verifier stack. The most urgent experimental questions are proving 8B is not only teacher-plan compression and proving graph structure beats a linear memory-tool chain.
